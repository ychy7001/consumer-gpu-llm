## 公开测试集

[evalscope](https://github.com/modelscope/evalscope) 1.14.1，OpenAI 兼容接口直连单个实例，thinking 关、temperature 0。三种部署同时跑、同题对比：

- **FP8 参考：** vLLM 0.25.1 + Qwen3.8-27B-FP8，单卡，即替换前的生产权重。
- **HQ batch：** HyperQwen batch 模式，10-31 起的生产配置。
- **HQ single：** single + MTP + PTH，16 槽，CG64。

| 数据集（题数） | FP8 参考 | HQ batch | HQ single |
| --- | --- | --- | --- |
| GSM8K（1319） | 96.82 | 96.59 | 96.97 |
| MMLU-Pro（14 科各 100） | 74.00 | 74.64 | 73.43 |
| C-Eval（val 1346） | 87.15 | 87.00 | 86.33 |
| IFEval prompt strict / loose（541） | 85.53 / 88.68 | 85.32 / 88.68 | 85.12 / 88.68 |
| DocVQA ANLS（val 前 500） | 95.61 | 94.85 | 94.96 |
| LongBench v2 short（180），输出上限 2048 | 57.22 | 53.89 | 51.67 |
| LongBench v2 short（180），输出上限 8192 | **64.44** | **63.89** | **62.22** |

- **差距是噪声。** 逐题配对（McNemar）：batch 对 single 五个文本集合计 4786 题，只有 batch 对的 183 题、只有 single 对的 158 题，z = 1.35（p ≈ 0.18）。单个数据集最大差 MMLU-Pro 1.2 个点，z = 1.44。GSM8K 和 DocVQA 上 single 反而更高。
- **W4A16 的代价在 DocVQA 上最明显，约 0.7 ANLS。** batch 与 single 同样低于 FP8，与模式无关。
- **LongBench 的输出上限会造成假差距。** 上限 2048 时 HQ 落后 FP8 3–6 个点，看起来像长上下文退化。逐题看，三种部署输出 token 中位数 1111 / 1104 / 1257，撞上限没写出答案的题 37 / 42 / 52 道，全部算错；只看抽到答案的题，准确率是 65.6 / 66.9 / 65.0，基本一样。上限提到 8192 后只剩 0–2 道题未完成，差距收到 0.6 / 2.2 个点，配对 z = 0.22 / 0.85。thinking 关闭时模型也会先写一大段分析，评测长上下文时输出上限要给足。
- 门槛原定"single 对 batch 每项 ≤1 个点、对 FP8 ≤2 个点"。MMLU-Pro 和 LongBench 名义上超了，但配对检验都不显著，按合并检验判通过。几百到一千多题的数据集，单项 1 个点本身就在一个标准误左右，门槛应写成"配对检验不显著"，而不是固定分差。

## single 与 batch：四卡同模式对比

四张卡先全部 batch，再全部 single + MTP + PTH（16 槽 CG64），经 Router 跑同一套负载。chat 是 1k 入 / 256 出，doc 是 16k 入 / 512 出；合计 = 输入 + 输出 tok/s。

| 负载 | 全 batch 合计 | 全 single 合计 | TTFT P50 / P99（batch → single） | TPOT P50（batch → single） |
| --- | --- | --- | --- | --- |
| chat c64 | 7,685 | 11,696（+52%） | 0.49 / 4.8 s → 0.96 / 6.3 s | 36 → 19 ms |
| chat c128 | 10,469 | 12,319（+18%） | 0.68 / 8.4 s → 6.2 / 13.2 s | 53 → 21 ms |
| doc c32 | 9,359 | 12,899（+38%） | 11.4 / 54 s → 10.4 / 36 s | 68 → 38 ms |

单路 decode（短上下文，c1 / c16 / c64 每路）：batch 55 / 53 / 46，single 115 / 93 / 74 tok/s。GSM200 经 Router（并发 32）：96.5% 对 94.5%，在 GSM200 单跑 ±3 题的抖动内。

single 唯一的短板是槽位：16 槽 × 4 卡 = 64 个在途请求，c128 时一半请求在排队，TTFT P50 从 0.7 s 涨到 6.2 s。下一节解决。

## 槽位数与 CUDA graph

GPU1 单卡直连，1k 入 / 256 出：

| 配置 | KV 池 | c24 TTFT P50 | c32 合计 | c32 TTFT P50 / P99 | c32 TPOT P50 | c48 TTFT P50 |
| --- | --- | --- | --- | --- | --- | --- |
| 16 槽，CG64 | 797,997 | 3.2 s | 3,426 | 6.3 / 9.5 s | 22 ms | 12.3 s |
| 32 槽，CG64 | 791,829 | 0.5 s | 3,322 | 0.6 / 6.7 s | 42 ms | 6.3 s |
| **32 槽，CG128** | 789,516 | 0.5 s | **3,738** | 0.6 / 6.8 s | 37 ms | 5.9 s |

纯 decode（输入 82 token，输出 512），c1 / c16 / c32：

| 配置 | 每路 tok/s | c32 合计输出 |
| --- | --- | --- |
| 16 槽，CG64 | 118 / 71 / 69 | 976（一半请求排队） |
| 32 槽，CG64 | 109 / 70 / 32 | 910 |
| 32 槽，CG128 | 123 / 72 / 46 | **1,338** |

- 16 槽在并发超过 16 后直接排队，TTFT 线性上涨。
- 32 槽 CG64 解决了排队，但 MTP 每步每路要算 1 + 3 个 token，32 路就是 128 个 token，超出 CG64 的部分退回 eager，c32 每路 decode 掉到 32 tok/s。
- CG128 覆盖 32 × 4，c32 每路回到 46 tok/s，合计 1,338 tok/s，是这张卡纯 decode 的峰值。混入 1k prefill 的对话负载下，c32 合计输出约 743 tok/s，容量估算用这个数。
- 16k 文档三档相同（c16 合计约 4,220 tok/s），长 prefill 不受槽位和 graph 影响。
- KV 池随槽位和 graph 只少约 1%。

## 整机容量（经 Router）

最终部署与切换前（3 batch + 1 single 16 槽 CG32）同一套负载，合计 = 输入 + 输出 tok/s，全部 0 失败。

| 负载 | 并发 | 切换前合计 | 最终合计 | 最终 TTFT P50 / P99 | 最终 TPOT P50 |
| --- | --- | --- | --- | --- | --- |
| chat 1k / 256 | 16 | 3,385 | 6,049 | 0.29 / 1.1 s | 10 ms |
| | 32 | 5,595 | 8,820 | 0.38 / 2.4 s | 14 ms |
| | 64 | 7,749 | 11,674 | 0.49 / 3.6 s | 22 ms |
| | 96 | 7,814 | 12,523 | 0.71 / 5.5 s | 31 ms |
| | 128 | 8,914 | 13,749 | 1.4 / 9.7 s | 36 ms |
| | 192 | 8,832 | 13,563 | 5.1 / 15.7 s | 39 ms |
| doc 16k / 512 | 4 | 3,660 | 6,739 | 3.9 / 7.8 s | 7 ms |
| | 8 | 6,262 | 8,440 | 4.6 / 12.7 s | 15 ms |
| | 16 | 8,645 | 11,706 | 6.3 / 21.0 s | 25 ms |
| | 32 | 10,337 | 14,016 | 8.6 / 41.9 s | 36 ms |
| | 64 | 11,433 | 15,856 | 19.1 / 69.8 s | 91 ms |

- 对话吞吐 +51–79%，16k 文档 +35–84%；GSM200 95.0%。
- chat 在 c128 附近饱和（4 卡 × 32 槽 = 128），c192 吞吐不再涨、TTFT P50 升到 5 s。按 TTFT P99 ≤ 5 s 算，整机可承载约 80–90 路并发对话。
- single 模式的 prefill 也更快：GPU1 单卡 16k 4,490 tok/s、64k 3,290 tok/s，batch 模式是 3,700 / 2,820。
- 混合负载（chat 与 doc 3:1）合计 c32 10,652、c64 13,161、c128 14,511 tok/s，比切换前高 18–28%。chat TTFT P99 分别是 10.4 / 18.1 / 41.5 s，与切换前同级，长 prefill 打断短请求的问题没有因为换模式而消失，见下文切块。

## 长文档

经 Router 的纯 prefill（输出 1 token），3 batch + 1 single 部署（最终部署复测：128k c1 56 s、200k c1 114 s，其余同级）：

| 输入 | 并发 | TTFT P50 / 最大 | 合计 prefill tok/s |
| --- | --- | --- | --- |
| 128k | 1 | 60 s | 2,169 |
| 128k | 4 | 60 / 61 s | 8,551 |
| 128k | 8 | 87 / 180 s | 5,792 |
| 128k | 12 | 120 / 223 s | 6,993 |
| 200k | 1 | 116 s | 1,770 |
| 200k | 4 | 120 / 240 s | 3,406 |
| 200k | 8 | 176 / 344 s | 4,738 |

- **单个长文档的 TTFT 由单卡算力决定：** 128k 约 60 s，200k 约 116 s，和旧的 TP2 部署相近（[baseline.md](baseline.md) 128k 约 68 s）。DP 只增加并发容量，不缩短单个请求。
- **power_of_two 不看负载，长请求会叠到同一张卡。** 200k 并发 4 时最大 TTFT 正好是单个的两倍（240 s），说明有两个请求进了同一张卡，另一张卡空着。后端 `/get_load` 返回 404，Router 拿不到真实负载（[dp4.md](dp4.md)）。长文档多的场景，应在客户端限并发，或给长请求单独一个入口。

## 混合负载与同卡混部

chat 和 16k doc 按 3:1 并发同时打（3 batch + 1 single）：

| 总并发 | chat TTFT P50 / P99 | 单独跑 chat 同并发 P99 | doc TTFT P50 |
| --- | --- | --- | --- |
| 32 | 0.53 / 11.5 s | 2.5 s | 5.1 s |
| 64 | 0.77 / 18.5 s | 4.6 s | 6.3 s |
| 128 | 4.7 / 30.8 s | 18.1 s | 10.4 s |

长 prefill 把同卡上短请求的首 token 往后推，P50 影响小，P99 放大 3–5 倍。

embedding 和 reranker 与 LLM 同卡：LLM 满载（chat c96）时 embedding P50 47 → 79 ms，reranker 44 → 56 ms，P99 都在 100–116 ms，可接受。

## 长 prefill 切块

vLLM V1 调度器的 `--long-prefill-token-threshold` 限制单个长请求每步占用的 token 数，给短请求留出预算。GPU3 单卡 batch 模式，64k 文档并发 2 加 chat 并发 24 同时跑：

| 配置 | chat TTFT P99 | 64k 文档 TTFT P50 | 单独 chat c24 TTFT P99 | 16k / 64k prefill tok/s |
| --- | --- | --- | --- | --- |
| mbt 2048（默认） | 24.7 s | 26.7 s | 6.2 s | 3,707 / 2,820 |
| mbt 4096 | 53.0 s | 26.6 s | 6.1 s | 3,720 / 2,858 |
| mbt 8192 | 54.0 s | 27.7 s | 6.0 s | 3,786 / 2,892 |
| mbt 8192 + 阈值 2048 | **12.2 s** | 42.4 s | 6.0 s | 3,784 / 2,888 |

- mbt 本身对 prefill 速度影响不到 3%。
- 阈值 2048 把混合负载下 chat P99 从 54 s 压到 12 s，代价是长文档 TTFT P50 慢约 55%。
single 模式（GPU1，32 槽 CG128）复核，同一负载：

| 配置 | 混合 chat TTFT P99 | 64k 文档 TTFT P50 | 单独 chat c24 TTFT P99 | 16k / 64k prefill tok/s | KV 池 |
| --- | --- | --- | --- | --- | --- |
| 默认（mbt 2048） | 47.1 s | 22.2 s | 5.0 s | 4,490 / 3,290 | 789,516 |
| mbt 8192 + 阈值 2048 | **9.1 s** | 40.1 s | 4.7 s | 4,672 / 3,473 | 769,469 |

结论与 batch 模式一致：混合负载下 chat P99 降到约五分之一，长文档首 token 慢约 80%，纯 prefill 和纯对话不受影响，KV 池少 2.5%。生产暂不开：现在没有业务流量，不知道文档与对话哪边更在意延迟。内测若反馈"有人传长文档时对话卡住"，在 `EXTRA_ARGS` 加这两个参数即可。

## 功耗

GPU3 单卡，`nvidia-smi -pl`，chat c96 经 Router：

| 上限 | 实测均值 | 单路 decode | 16k prefill | chat c96 合计 |
| --- | --- | --- | --- | --- |
| 450 W（默认） | 379 W | 125 | 3,801 | 8,545 |
| 350 W | 334 W | 113 | 3,663 | 8,561 |
| 300 W | 291 W | 109 | 3,463 | 7,946 |
| 250 W | 247 W | 107 | 2,854 | 7,503 |

300 W 是拐点：功耗降 23%，decode 降 13%，prefill 降 9%。250 W 时 prefill 掉 25%。生产保持默认；机房供电或散热紧张时设 300 W。

## 故障切换

单独起一个 Router 挂 4 个 worker，chat c32 持续压测。第 60 s kill 一个后端，第 150 s 重启，它在 t = 247 s 重新就绪：

| Router 参数 | 成功 / 2400 | TTFT P99 | 就绪后重新接流 |
| --- | --- | --- | --- |
| 默认（健康检查 60 s，失败阈值 3，熔断 60 s） | 2394 | 1.45 s | 117 s |
| 快速（5 s，阈值 2，成功阈值 1，熔断 10 s） | 2393 | 1.29 s | **11 s** |

- **失败数与参数无关：** 两种都只失败 6–7 个请求，就是 kill 那一刻落到该后端的那些。连接错误后熔断器立即打开，之后的请求都分到其余三张卡。
- **区别在恢复：** 默认熔断 60 s 一个周期，后端刚启动时 half_open 试探失败又打开，就绪后还要再等约两分钟才接流。快速参数 11 s 内接回。
- 计划内的重启（切换、升级）走 `remove_worker` / `add_worker`，不依赖熔断。快速参数只在意外崩溃时少浪费两分钟单卡容量，生产可以改，但不是必需。
